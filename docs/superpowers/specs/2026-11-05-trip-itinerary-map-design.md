# 여행 일정 공유 지도 Webapp 설계

## 의도

확정된 여행 일정을 참가자들이 한눈에 확인하고, 각 일정의 시간과 장소 사이 이동 순서를 지도와 함께 공유한다. 개발 시 기본 일정을 넣어 배포하고, 여행 중에는 주최자 한 명이 웹에서 변경하며 모든 참가자가 같은 최신 내용을 본다.

## 목표

- 날짜별 일정과 시간순 방문 순서를 읽기 쉽게 보여준다.
- 장소, 체류 시간, 메모, 이동 수단과 다음 장소까지의 이동 시간을 보여준다.
- 일정 지점과 이동 경로를 지도에 표시하고 목록 선택과 지도 선택을 연결한다.
- 주최자만 일정 항목을 추가·수정·삭제하고 순서를 조정할 수 있다.
- 수정 내용은 서버에 저장되어 다른 기기의 읽기 화면에 반영된다.

## 비목표와 실패 조건

- 여러 여행을 관리하거나 참가자별 계정을 제공하지 않는다.
- 실시간 공동 편집, 댓글, 알림, 예약·결제 기능은 포함하지 않는다.
- 장소명을 입력해 자동으로 좌표를 찾는 지오코딩은 포함하지 않는다. 초기 데이터와 편집 화면에서 좌표를 제공한다.
- 지도 타일을 직접 호스팅하지 않는다.
- 수정이 수정한 브라우저에만 남거나, 읽기 화면에서 편집 권한이 노출되는 것은 실패로 본다.

## 제약과 기본 가정

- 저장소가 비어 있으므로 별도 프레임워크 없이 Node.js 기본 HTTP 서버와 정적 HTML/CSS/JavaScript를 사용한다.
- 일정 원본은 `data/itinerary.json`으로 배포하고, 서버가 같은 파일에 수정 내용을 저장한다.
- 읽기 화면은 `/`, 편집 화면은 `/?edit=1`로 진입한다.
- 쓰기 API는 환경변수 `EDITOR_TOKEN`과 Bearer 토큰으로 보호한다. `?edit=1`에서 토큰을 입력받고 브라우저 `sessionStorage`에만 보관하며, 로그아웃하면 제거한다. 토큰이 없거나 틀리면 편집 화면도 읽기 전용으로 동작한다.
- 지도는 Leaflet을 CDN으로 불러오고 OpenStreetMap 타일과 필수 출처 표기를 사용한다.
- 단일 여행 일정과 단일 편집 권한만 지원한다.

## 접근 방식

1. 정적 페이지와 `localStorage`: 가장 작지만 수정 내용이 다른 기기로 공유되지 않아 요구사항에 맞지 않는다.
2. 작은 Node 서버와 JSON 파일 저장: 외부 데이터베이스 없이 초기 데이터와 여행 중 수정 데이터를 같은 URL에서 공유할 수 있다. 선택한 방식이다.
3. 관리형 백엔드(Supabase/Firebase): 인증과 동기화는 강하지만 서비스 설정과 의존성이 늘어나 현재 단일 편집자 범위보다 크다.

## 화면과 흐름

읽기 화면의 기본 배치:

```text
┌─────────────────────────────────────────────┐
│ 여행 제목 · 날짜 탭 · 마지막 저장 시각       │
├───────────────────┬─────────────────────────┤
│ 09:00  공항 출발  │                         │
│ 이동 35분         │          지도            │
│ 10:00  호텔 체크인│    마커 + 경로 선         │
│ ...               │                         │
└───────────────────┴─────────────────────────┘
```

- 날짜 탭을 선택하면 해당 날짜 일정과 지도 범위를 갱신한다.
- 일정 항목을 선택하면 해당 마커를 강조하고 지도 중심을 이동한다.
- 목록에는 시작 시각, 장소명, 체류 시간, 메모를 표시한다.
- 항목 사이에는 이동 시간과 이동 수단을 표시하고, 지도에는 순서대로 선을 연결한다.
- 모바일에서는 목록 위에 지도, 또는 지도와 목록을 세로로 배치해 좁은 화면에서도 시간순 읽기를 유지한다.
- 편집 모드에서는 항목별 편집/삭제, 새 항목 추가, 위·아래 이동, 저장/취소를 제공한다. 읽기 화면에는 편집 입력 요소를 표시하지 않는다.

## 데이터와 API

일정은 다음 필드를 갖는다: `id`, `date`, `startTime`, `title`, `location`, `note`, `durationMinutes`, `transportToNext`, `travelMinutesToNext`, `lat`, `lng`.

- `id`는 서버가 생성하는 UUID 문자열이며 저장 중 유일해야 한다.
- `date`는 `YYYY-MM-DD`, `startTime`은 `HH:mm` 형식이고 모두 여행 현지 시간으로 표시·정렬한다.
- `durationMinutes`와 `travelMinutesToNext`는 0 이상의 정수다. 마지막 항목의 이동 필드는 `null`로 둔다.
- 장소가 지도에 표시되도록 `lat`와 `lng`는 모든 항목에 필요하며, 위도 `-90..90`, 경도 `-180..180` 범위를 검증한다.
- 항목 배열 순서가 표시 순서다. 위·아래 이동은 같은 날짜 안에서만 가능하고, 날짜를 바꾸면 서버가 날짜별로 다시 표시한다.

- `GET /api/itinerary`: `{ itinerary, updatedAt }` 반환
- `PUT /api/itinerary`: `{ itinerary: [...] }`를 받아 전체 일정 교체 저장. `updatedAt`은 서버가 UTC ISO 문자열로 생성하며, 유효성 검사를 통과한 경우에만 파일을 원자적으로 갱신한다. 실패 시 400 또는 401과 `{ error }`를 반환한다.
- 정적 파일: 읽기 화면, 편집 화면, 스타일, 클라이언트 스크립트

클라이언트는 화면 진입 시 한 번 읽고, 저장 성공 후 다시 읽는다. 읽기 화면의 새로고침으로 최신 변경사항을 확인한다. `updatedAt`은 사용자의 브라우저 로케일로 표시한다. 동시 편집 충돌 해결은 범위 밖이며, 서버는 마지막으로 성공한 저장을 보존한다.

## 성공 기준

- 기본 JSON으로 서버를 시작하면 일정 목록과 지도 경로가 표시된다.
- 날짜를 바꾸면 목록, 마커, 경로가 함께 바뀐다.
- 편집 토큰이 없는 사용자는 읽기 화면만 볼 수 있고 PUT 요청은 거부된다.
- 편집자가 항목을 추가·수정·삭제·이동한 뒤 저장하면 서버 파일과 다른 기기의 새로고침 화면에 반영된다.
- 잘못된 시간, 좌표, 필수 제목을 가진 저장 요청은 거부되고 기존 일정은 유지된다.
- 모바일 폭에서도 목록의 시간과 장소, 지도 조작이 겹치지 않는다.

## 구현자에게 남기는 결정

- 서버 포트, 기본 일정 샘플, 시각적 색상과 세부 타이포그래피는 구현자가 정한다.
- 파일 저장은 한 번에 하나의 저장만 처리하도록 간단한 직렬화 또는 임시 파일 교체를 사용한다.
- 지도 타일이 로드되지 않는 경우에도 목록과 위치 좌표는 사용할 수 있게 한다.
